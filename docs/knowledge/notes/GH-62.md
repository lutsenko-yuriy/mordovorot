# GH-62: Move counter

## Notes

### 2026-10-14

**Deferred review findings (kept as notes, not tickets)**

- `SaveRepository.save` and `BoardModel.restoreState` default `moveCount` to 0, so a future
  save path (e.g. an autosave) that forgets the count compiles and silently writes 0.
  `ViewModelImpl.saveGame`/`loadGame` are the only callers today and pass it. Revisit if a
  second save/load path appears (PR #69 review comment).
- `BoardLayout.fullHeight` doesn't count the mode, message and controls-hint rows below the
  toolbar, so on short terminals they clip off-screen. Pre-existing; GH-62's moves row moved
  it one row sooner (5x5 in a 22-row terminal now clips the keyboard hint). 80x24 still fits
  (PR #69 audit comment).

## Debrief summary

### 2026-10-14

**What went well**
- Faster and easier than expected - user: "I thought it would be more difficult, but you
  made it quickly!" Plan → scenario stubs → six TDD phases → PR in one pass; the scenarios
  passed first run and a mutation check (forcing `Moves: 0`) failed 7 of 11.

**What was hard or surprising**
- The first plan put a `restoredFromSave` flag on the board; the user caught that restoring
  from a save is app logic, not domain logic, and it was dropped. One-off slip - keep in mind
  when placing new fields, no skill change.
- During the TUI phase a commit went in while the test run reported a failure: the test
  output was piped through `grep`, which hid the exit code. A clean build showed it was a
  stale incremental compile, so nothing broken shipped. One-off slip - check the real exit
  status before committing, no skill change.

**What to change**
- No workflow changes. The two deferred review findings stay as notes (above) rather than
  tickets.
