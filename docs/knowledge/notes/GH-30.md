# GH-30: GameSession session loop and mode switching

## Notes

- 2026-09-14: Audit finding on PR #36 - GameSession.run() treats any normal View.play() return as "session ended" and exits the whole process, but ConsolePresenterImpl.play() also returns immediately, with zero output, when board.isCorrect() is already true on entry (the same design ConsolePresenterStartupRestoreTest already covers deliberately for the startup-restore-onto-a-solved-save case - see its class KDoc). Pre-GH-30 this equivalence was harmless (both paths ended the one-and-only Main() call the same way). Post-GH-30 (once WU2/WU3 add the console `mouse`/`keyboard` command and TUI toolbar mode-switch affordances), a user who solves the board in mouse/keyboard mode and then explicitly switches to console mode will instead have the entire application silently exit - the mode-switch request is indistinguishable, at the View.play(): Unit boundary, from a deliberate quit. Not fixed in WU1 because a real fix needs either (a) a product decision on what console mode's solved-state UX should even be (docs/PRODUCT_SPEC.md's "Known gaps" section already flags "Console mode has no documented win-condition message" as unresolved), or (b) a View/Presenter contract change (play() signaling *why* it returned) that's a bigger surface than WU1's plumbing-only scope. Follow-up ticket: decide console mode's solved-state behavior (at minimum, GameSession must not silently exit the whole app on a switch onto an already-solved board) and implement it.
- 2026-09-15: Audit finding (round 2) on PR #37 - GameSession.run()'s crash-recovery fallback (added to fix round-1's crash risk) is untracked in analytics. ModeSwitcher.switchTo tracks input_mode_switched with result=success at request time, before GameSession even attempts to rebuild the View for the target mode - so if that rebuild then fails and GameSession falls back to console (e.g. a real-world stty failure), the event still says the switch to mouse/keyboard succeeded, even though the user ended up back in console. docs/ANALYTICS_EVENTS.md's input_mode_switched only documents result values success | rejected_no_tty - no way to represent "requested, initially reported success, but then failed and fell back." Not fixed as part of PR #37 because it's a real analytics/product design question (does this need a new result value like fallback_failed, or a separate event fired from GameSession itself, which currently has no analytics service reference passed down for this purpose?) rather than a quick fix. Follow-up: decide how (or whether) to make this failure mode observable in analytics, and implement it.
