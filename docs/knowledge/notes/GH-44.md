# GH-44: Adjustable board size (3x3-5x5, default 4x4)

## Notes

## Debrief summary

### 2026-09-16

**What went well**
- All the practices that mattered were already codified in the docs going into implementation - nothing new needed there.

**What was hard or surprising**
- Turned out much more complex than expected, driven by the multi-WU split: the original plan had 3 WUs, but it ended up as 5 (WU0 scenario stubs, WU1 domain + launch flag, WU2 startup prompt, WU3 new-game surfaces, WU4 save size visibility, WU5 load auto-resize).
- The save/load interaction with variable board size (a save could now be a different size than the live board) wasn't part of the original plan - the user only remembered it needed handling closer to the end, which then split into two more WUs (WU4 visibility, WU5 auto-resize behavior).
- Auto-resize itself (WU5) turned out more complex than anticipated once in progress - see the audit finding on PR #55 about `BoardImpl.restoreState` needing its own `BoardSize` range check once the "must match the board's current side" guard was removed.

**What to change**
- No workflow/skill change adopted this round - the user attributes the scope growth to a one-off recall gap (remembering the save/load interaction late) rather than a process gap in `brief`/`plan`. Revisit if this pattern (a persisted-state interaction surfacing late in a ticket that changes a previously-fixed domain invariant) recurs on a future ticket.
