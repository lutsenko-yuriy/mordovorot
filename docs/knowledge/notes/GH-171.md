# GH-171: Web: keyboard play

## Notes

- 2026-10-30: (for debrief) the /brief session was long and intensive — about 17 one-question turns walking through every web detail #169/#189 had deferred (focus, mouse in keyboard mode, touch, Controls focus, four screen-reader cases, Read board key, first visit, solution screen, analytics, selection look, hints, toolbar). The user said this is expected for such a ticket, but wants to find a way to shorten such sessions in the future. Ideas to weigh at debrief: batch low-stakes forks into one "defaults unless you object" turn (as was done once for the solution-screen focus defaults, which the user accepted in one reply), or settle deferred details in the design ticket (#169/#189) itself.
- 2026-10-30: **Amendment: the flag (D3).** `keyboardModeEnabled` was `false` in `Main.kt` until WU4; now it's `host == Host.LOCALHOST` until WU4. Why: fully off, neither the headless harness (served on 127.0.0.1) nor the player trying a WU on the dev server could reach Controls, and the plan's `keys_check.sh` flows and `measure.sh "input=keyboard"` need it. The public site is unchanged: off. Came up in WU2.
- 2026-10-30: **Amendment: the board's role (D4).** The plan's fallback (a), `role="table"` + `tabindex="0"`, becomes (b), `role="grid"` with `aria-activedescendant` on the selected cell. Why: the Research-WU below. The user approved it after the research. Three terms come with it:
  1. `aria-activedescendant` points at the selected cell before the board takes focus, since focus on the grid container alone doesn't switch NVDA's mode (inferred from NVDA's code; no source states it).
  2. The ticket's selection words may double with what the reader says for the cell. The user's VoiceOver test in WU3 decides; a wording change gets its own amendment here.
  3. NVDA and JAWS stay untested unless someone tries them on Windows, and the ticket ships with that risk stated. A player with stuck keys can use `NVDA+Space`.
- 2026-10-30: **Amendment: where the board is a Tab stop until WU4.** The plan has `boardFocusable` true during play and on the solution screen; WU3 makes it `WebState.selection != null`, play only, since the solution keys come in WU4. Why: a Tab stop that takes no keys would be worse than none for a WU. WU4 extends it. Also from WU3: held select and shift keys repeat, as in the terminal (the ticket doesn't say); a held digit still presses once.
- 2026-10-30: (for WU4, from the user's VoiceOver test in WU3) on a selection move VoiceOver already says the new cell itself, and the user wants it to stop the old tile for the new one. So a selection move no longer rebuilds the board: it changes `aria-activedescendant` in place, each cell with its own id. WU4: words sent through the polite live region queue instead of interrupting, so don't add selection words there without checking; this may need an amendment to D4's term 2 and the ticket's `delta, row 2, column 4`.
- 2026-10-30: **Research-WU (D4), single pass.** Thesis: (a) `role="table"` + `tabindex="0"` + live region is enough. Antithesis: it needs (b) `role="grid"` + `aria-activedescendant` or (c) `role="application"`. No source tested these exact setups on a real screen reader.
  - **Keys.** NVDA: (a) fails. A focused table stays in browse mode ([`browseMode.py`](https://raw.githubusercontent.com/nvaccess/nvda/master/source/browseMode.py): the always-switch list has rows, cells and headers, not `TABLE`; read, not run), where the [User Guide](https://download.nvaccess.org/documentation/userGuide.html) shows the letters taken or trapped. Focus on the grid container doesn't switch either ([`aria.py`](https://raw.githubusercontent.com/nvaccess/nvda/master/source/aria.py) maps `grid` to `TABLE`); focus on a cell does ([#5118](https://github.com/nvaccess/nvda/issues/5118), Twitter's J/K, 2015). JAWS: probably the same, on one old source ([bulletin 1665](https://web.archive.org/web/2024/https://www.freedomscientific.com/Support/TechnicalSupport/Bulletin/1665): Forms Mode for grid cells, plain tables not listed). VoiceOver: no separate browse mode ([Watson](https://www.creativebloq.com/netmag/aria-s-application-role-4135685)), but no source confirms keys reach the page; [Quick Nav](https://support.apple.com/en-mo/guide/voiceover-guide/vo27943/web) applies only if enabled.
  - **Double speech.** Open: no source tests a live region alongside any option. Nearest: [Walker](https://webaim.org/discussion/mail_message?id=37377) on text in a live region that also takes focus, [Biggs](https://webaim.org/discussion/mail_message?id=36129) on an NVDA ARIA grid reading cells twice.
  - **Table reading.** (b) works on current NVDA, JAWS and VoiceOver ([PowerMapper](https://powermapper.com/tests/screen-readers/tables/table-role-grid), date conflicts: 2022 or 2025; reading only, no key handling). In focus mode users hear only focusable content ([APG Grid](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)); `NVDA+Space` returns to browse mode (mailing-list post only).
  - **(c) dropped.** [WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/) keeps `application` for when no widget role fits, [Watson](https://www.creativebloq.com/netmag/aria-s-application-role-4135685) and [Zehe](https://marcozehe.de/if-you-use-the-wai-aria-role-application-please-do-so-wisely/) advise against it, and NVDA's `shouldPassThrough` doesn't special-case it.
  - **VoiceOver and `aria-activedescendant`.** Past gaps, reported fixed in macOS 15 ([#231993](https://bugs.webkit.org/show_bug.cgi?id=231993), [#269026](https://bugs.webkit.org/show_bug.cgi?id=269026); the latter's fix rests mainly on comments).
  - **Evidence limits.** No current JAWS source. Some quotes came through a summarising fetch; recheck before citing elsewhere.
