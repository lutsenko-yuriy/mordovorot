# GH-163: Web: dialogs work from the keyboard

## Notes

## Debrief summary

### 2026-10-25

**What went well**
- Overall it went quite well: the brief widened the ticket from "focus on open" to the whole dialog keyboard story (focus on open and close, Tab kept inside, names, Escape) in four short questions.
- Putting every focus rule in `commonMain` (plan D1) made each brief decision a scenario assertion; the browser code only applies a `data-focus` key.
- The headless smoke page caught the one surprise before the user saw it: Chrome rings a script-focused button on a fresh load, so rings now wait for the first key press (plan D3 b).

**What was hard or surprising**
- Testing by hand was tedious but necessary: clicking through every dialog and dealing with VoiceOver, unguided.
- The real-browser runtime differed from the tests in ways only the audit found: Safari's IME Escape (keyCode 229 after `compositionend`) and a held Escape's repeat cancelling the next dialog in a chain.

**What to change**
- `docs/workflows/FEATURE.md` step 10.0: for web keyboard and screen-reader changes, check headless everything it can show, then give the user a short per-flow checklist of only what it can't (VoiceOver speech, ring look).
- #174: commit GH-163's throwaway smoke page as a harness mode, so #164, #166, #167 and #171 reuse it.
