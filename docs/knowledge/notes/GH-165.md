# GH-165: Web: colour contrast and colour-blind check

## Notes

- 2026-10-26: During /plan the user had to approve D5 (colour-blind safety) on a concept they had almost never dealt with, and only afterwards asked for a general explanation of colour-blind design techniques (no colour alone, lightness over hue, safe palettes like Okabe–Ito, patterns/symbols, colour-blind modes, simulators). Idea: when a brief/plan decision rests on a domain concept the user may not know, the workflow should prompt them (or offer) to ask about it / get a short primer before deciding. The user also floated filing a ticket for this in YAB-dev; decide at debrief whether to file it there.

## Debrief summary

### 2026-10-26

**What went well**
- Overall the ticket went well: plan, red test, green colours and docs in one session; the audit found nothing and the one review comment (pairs read from their rules) was fixed in one commit.
- The before/after comparison page (with a colour-blind Vision switch) let the user see the palette before any code was written.
- Keeping a small hand-rolled WCAG test over axe-core or a colour library: it covers every tile of every board in both themes without a browser in CI.

**What was hard or surprising**
- D5 (colour-blind safety) was approved before the user knew the field; the primer came afterwards. The "now vs proposed" doubt on the comparison page came from the same gap.

**What to change**
- `brief` offers a short primer when a ticket rests on a concept new to the project (not in the spec or glossary); `plan` proposes a Research WU when the concept is too big for a primer or only surfaces during planning. No new PoC WU type: the Research WU covers it.
- Same change for the YAB harness: lutsenko-yuriy/yab-dev#29.
