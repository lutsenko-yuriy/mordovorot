# GH-220: Research: smaller saves (a compact save format, maybe obfuscated)

## Notes

### 2026-11-02

**Scope (RESEARCH.md step 1)**

One kind of question: the shape of a save. How a new format sits beside the old one is part of that shape, so the ticket was not split.

Ticket-specific constraints:
- The only store is the browser's `localStorage` (the terminal is gone, GH-228). It holds text only, 5 MiB per origin, and throws `QuotaExceededError` at the limit ([MDN, storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). MDN doesn't say whether the 5 MiB counts bytes or UTF-16 characters, so the numbers below assume the worse case, 2 bytes per character.
- Common Kotlin only (the codec runs on the JVM tests and in the browser). `kotlin.io.encoding.Base64`, with its `UrlSafe` variant, is in the common stdlib and stable since Kotlin 2.2 ([Kotlin API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.io.encoding/-base64/)); the project is on 2.4. `java.util.zip` is JVM-only, and the browser's `CompressionStream` is asynchronous, so a compression step would need `expect`/`actual` code.
- Pre-launch, no users to protect (`docs/CONSTRAINTS.md`), so an old build failing on a new save is acceptable; old saves still have to load.
- Decided in the brief: saves may become opaque to a human (obfuscation is a welcome side effect, not a goal); the walkthrough file of GH-215 is dropped, the save format is enough (GH-215 closed); Mordie's solution goes last; under 1 KB is a **Should**.

| | Goal |
|---|---|
| Must | Lossless round trip of everything a save holds today |
| Must | Old text saves keep loading |
| Must | Works in common Kotlin on the JVM and in the browser |
| Must | Real sizes on 3x3 to 9x9, with and without Mordie's solution |
| Should | Worst case under 1 KB (1,024 characters as stored) |
| Should | A marker that tells the new format from the old |
| Could | Fewer bits through entropy coding; a checksum |
| Won't | Encryption or cheat protection; production code |

**Survey**

| Source | What it gives |
|---|---|
| [Protocol Buffers encoding](https://protobuf.dev/programming-guides/encoding/) | Varints: 7 bits per byte plus a continuation bit, so a small number takes 1 byte. Used here for the move count and for N and R. |
| [Lehmer code](https://en.wikipedia.org/wiki/Lehmer_code) and the factorial number system | A permutation of n items as digits of shrinking range. `ceil(log2(k))` bits for the digit with k values left comes to about 440 bits for 81 tiles (the information limit is about 401), and every bit pattern decodes to a valid arrangement. |
| [Kotlin `Base64.UrlSafe`](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.io.encoding/-base64/) | Turns bytes into characters safe for a key or value: 6 bits per character, so a third of the size comes back. |
| [MDN, storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) | The 5 MiB per-origin figure above. |

**Measurements (a throwaway Kotlin test, JVM, not kept in the repo; the code is in a comment on the issue)**

"Dense text" is a computed estimate (one character per tile, two per move), not an encoder. The packed columns are real encoders; the Lehmer + joint one round-trips losslessly on 10 games per side. The packed columns add 1 character for a format marker.

**Findings**
- A 9x9 text save is about 2.1 KB, of which the solution is about 1.5 KB (72%). 6x6 is already about 0.9 to 1 KB. The two boards as text are about 500 characters.
- Bit packing into base64url meets the 1 KB Should on every size, with the best candidate at 603 characters on 9x9 (about 3.6x smaller than text). Even plain fixed-width bits reach 700.
- Lehmer boards save about 6% on 9x9, the joint move code (axis, index and shift as one number) about 8%, and only where the widths differ (3x3, 5x5, 6x6 and 9x9; none on 4x4, 7x7 and 8x8). Both are small and cheap to write. The joint code is one expression; the Lehmer code is about 15 lines, and it makes every bit pattern decode to a valid board.
- Deflate on top of the packed bytes gains nothing (591 against 584). Compression is out.
- Entropy of the move symbols is 6.84 bits per move on 9x9, against 8 fixed. Arithmetic or Huffman coding would save at most about 15% of the solution part, 60 characters, for a lot of code. Out.
- Dense text meets the Should only barely (851 on 9x9) and is 2.6x smaller, and it keeps a save readable. It loses to bit packing on size, and the user decided readability isn't needed.
- Dropping the solution from the save would leave 156 characters on 9x9. Only the fast solver's answer can be recomputed (in milliseconds); the exact search's shorter answer cannot, and GH-224 keeps it. A recompute would also need the fast solver's output frozen, or an old save's N would change under a new build. Not recommended now; stays a Could.
- Quota: assuming 2 bytes per character, a 9x9 text save takes about 4.2 KB and a packed one about 1.2 KB, so about 1,250 saves against about 4,300 in 5 MiB. The pressure on the quota is small either way; the gain is the size the user asked for.
- Compatibility: `SaveFileCodec` is used in one production place, `BrowserSaveRepository`. Five test files write save text by hand or call the codec directly (`SaveFileCodecTest`, `SaveFileCodecProvenTest`, `BrowserSaveRepositoryTest`, `ViewModelMordieTest`, `WebAnnounceFlowsScenarioTest`). The old text format stays readable (the first character of a save is a digit, so a marker that isn't a digit tells the two apart). An old build can't read a new save and reports it as corrupted; the GH-139 habit of older builds ignoring what they don't know holds only for new lines in the old format. Acceptable while pre-launch.
- Obfuscation: a base64 packed save is opaque to casual editing, and trivially decodable by anyone who reads the format. There is no checksum; with Lehmer boards a random edit still decodes to a valid board, but a corrupted solution can decode to moves that don't solve it, which the existing load check ("Mordie's solution doesn't solve the original arrangement") already rejects.

**Recommendation**

A new save format, written by a new codec, beside the old text format (read-only from then on):
- A marker character that isn't a digit, then base64url of a bit stream: side minus 3 (3 bits), labels (3 bits with an escape for an unknown one), status (2 bits: searching, proven, unproven) and two flags (solution screen, has solution), the move count as a varint, the current board then Mordie's original as Lehmer codes, N as a varint, R as a varint when unproven, and last the solution as one joint move code each.
- No compression, no entropy coding, no checksum for now.
- Result: every save under about 610 characters on all sizes, so the Should is met with a 40% margin.

Follow-up work (one feature ticket, GH-237; ADR-0004 records the decision): the codec behind `BrowserSaveRepository` with a decode that reads both formats, tests that cover round trips on every size and every old save shape (the old `SaveFileCodecTest` cases stay as decode tests), and the docs. Probably two WUs: the new codec with its tests, then the switch and the migration of the tests that write save text by hand.

## Debrief summary

### 2026-11-02

**What went well**
- Measuring real sizes before recommending anything settled the question: the solution is 72% of a 9x9 save, compression and entropy coding gain nothing worth their code, and a bit-packed save lands under 610 characters on every size.
- The user's own bit-field sketch (side in a few bits, tiles in fixed widths, moves as `row or column + index + shift`) was the winning design; the research confirmed it and added the permutation code, a varint move count and a joint move code.
- The brief and the research pulled in the decisions that shaped the result: saves may be opaque, 1 KB is a Should, the solution goes last. The packed format also makes a header-first, solution-last layout fall out naturally.
- One class (`BrowserSaveRepository`) is the only production caller of the codec, so the follow-up (GH-237) is small and the old format can stay read-only.

**What was hard or surprising**
- Readability of a save was only settled mid-session; the user said they should have mentioned it first. Not a workflow gap, so no change.
- GH-215 (a walkthrough file) was closed during the brief on a mix-up: a save already holds Mordie's solution as text, but it isn't a file the player can open. The user decided to keep it closed, since the save format is enough.
- The quota is under much less pressure than the ticket assumed (about 1,250 text saves against about 4,300 packed in 5 MiB), so the gain is the size the user asked for, not the storage limit.
- `:web:serve -t` started no server from the agent's shell this session; a static server on the built bundle stood in for a manual try-out.

**What to change**
- Nothing; no workflow or skill files changed.
