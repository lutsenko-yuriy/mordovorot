# GH-282: Mordie's exact search does not advance on the phone

## Notes

### 2026-11-15

**Why the phone was slow, and what shrank the search**

The search worked, but the user's iPhone (iOS 18.7; Firefox and Safari) runs plain JavaScript about 38x slower than desktop Chrome, in a worker and on the main thread alike, so scripts seem not to be compiled. The ticket board `2,15,1,0,4,5,9,8,3,7,12,6,14,11,13,10` was ruled out up to 10 in 11.8 s and proven at 11 in 165 s (desktop: 0.4 s and 5.6 s). The page shows only the move count, so "47" looked frozen. Two changes, no new behaviour:

- WU1 (0.44.2): per-move tables instead of `/` and `%`, and the child's cheap bound read off the moved line before rotating. Same search tree (34,511,703 expands), 2.8x less time per node under `node --jitless`.
- WU2: a pattern database (row 0 + the first tile of row 1, 5 tiles on 4x4), read through its 32 symmetric copies (16 torus translations x transpose), lazily and only when the cheap bound passes, stopping at the first copy over the limit. It is built by BFS in slices beside the exact search and switched in when whole.

**Measurements** (a JS port of the solver; `node --jitless` stands in for the phone, which is about 1.6x slower in CPU and 2x more from the 10/10 duty cycle)

| Bound | Expands, ticket board |
|---|---|
| cheap bound (today) | 34.5 M |
| max of 4-tile tables (rows + columns, 8 tables) | 15.2 M |
| 4-tile tables, 40 lookups | 11.7 M |
| **5-tile table, 32 lookups** | **2.10 M** |
| two 5-tile tables, 64 lookups | 1.53 M |
| 6-tile table | 0.31 M (21 s build, 16 MB: not for a phone) |

On other 4x4 boards the 5-tile table cut the tree 12x to 38x. On 3x3 (every board, against the oracle) it never overestimates and cuts sampled trees 7.9x. Time per node, jitless: 52.7 s before; 18.6 s with the cleanups; 4.1 s with the lazy table (12.7x). The table build is 524,160 states: 160 ms with compiled scripts, 2.7 s jitless, about 8.5 s on the phone. Extra pruning or a visited table would save 6-10% at most (pruned sequences against distinct states: 1.000 up to depth 3, 1.059 at depth 5), so neither was added.

**Why it stays exact:** the table is the exact distance on a simplified board, so it is admissible. Translations and the transpose map the move set onto itself, so every copy is a lower bound, as is their maximum. An early exit still leaves a valid `nextBound`, and a table that comes in mid-search is just another admissible bound.

References: Culberson & Schaeffer 1998 (pattern databases); Korf 1997; Felner et al. (symmetric lookups).

## Debrief summary

### 2026-11-15

**What went well**
- The phone diagnosis came before any fix: timeline pages in the worker and on the main thread showed the phone runs plain JavaScript about 38x slower, so the plan aimed at the real cause.
- The plan's measurements (a JS port under `node --jitless`) set the design, and every decision D1-D8 was taken as recommended with no rework.
- The audit's equivalence testing (old against new solver on tens of thousands of boards, resumed searches, the table switched in mid-search) found no correctness problem and caught a real regression: the table's allocation delayed the first answer and `search_duration_ms`. It took two rounds to fix properly.
- The phone check confirmed both timings, ruled out 10 and proven 11, were considerably faster (not timed), and the phone stayed lukewarm, which the user found acceptable.

**What was hard or surprising**
- Nothing slowed the ticket down beyond expectations.
- The cause on the phone itself (no JIT) is inferred from timings, not confirmed.
