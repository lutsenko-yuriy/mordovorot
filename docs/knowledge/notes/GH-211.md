# GH-211: Research: where and when Mordie thinks (Web Worker, idle-time search)

## Notes

### 2026-11-01

**Scope (RESEARCH.md step 1)**

Split out of GH-116, so this ticket is engineering only: where the browser's search runs and when Mordie thinks. Ticket-specific constraints: the site is static on GitHub Pages with no control over response headers (shared memory between a worker and the page, and Wasm threads, need cross-origin isolation headers, so they may be unavailable; to verify); "where" is a browser question, since the terminal's search already runs on a JVM thread, while "when" is shared game design; the web client is Kotlin/JS, so Kotlin/Wasm would be a new target and prototypes use the project's stack; measurements run in headless Chrome with a throwaway profile, never the user's browser, and headless Chrome may not throttle hidden tabs the way a real one does; until GH-213 and GH-214 exist the existing exact search is the workload, and the fast solver will cut what the page's thread carries to the exact search's improvements.

**Measurement 1: does the current search hurt the page? (headless Chrome, visible tab)**

GH-110's `[human]` checklist item was meant to give this number, but its notes record no measurement, so it was taken here. A scratch page loads the built game in a same-origin iframe (390x844), starts a game of each size and, for 8 s, records the gaps of a 4 ms timer in the parent page (which shares the game's main thread, so any blocking by the search shows up as lag) and the animation-frame intervals; it then clicks an arrow and times it to the second frame. The 3x3 and 6x6 runs are controls: on 3x3 the search ends at once, and Mordie sits 6x6 out. Throwaway code in the scratchpad, nothing in the repo; headless Chrome with a throwaway profile on this Mac, so a fast machine.

| Board | Search | Timer lag p50 / p95 / max (ms) | Gaps over 50 ms | Frame interval p50 / max (ms) | Click to 2nd frame (ms) |
|---|---|---|---|---|---|
| 3x3 | ends at once | 0.6 / 1.2 / 2.3 | 0 of 1728 | 16.7 / 16.8 | 27.7 |
| 4x4 | running | 0.6 / 8.2 / 8.6 | 0 of 1169 | 16.7 / 16.8 | 20.2 |
| 5x5 | running | 0.6 / 8.2 / 8.7 | 0 of 1172 | 16.7 / 16.8 | 23.3 |
| 6x6 | sat out | 0.6 / 1.3 / 26.3 | 0 of 1730 | 16.7 / 16.8 | 29.9 |

- A running search delays the page by at most about 9 ms, and no frame was dropped: the frames stay at 16.7 ms, and a click answers as fast as in the controls. So on a desktop-class machine the search does not make the page unresponsive, which is what the 10 ms slices were meant to guarantee.
- The delay is a slice's length, not the CPU's speed: the work is time-bound, so the lag should stay near 10 ms on a slower phone, plus the overshoot of one batch of nodes, which this run did not test on slow hardware.
- Not measured: a slow phone (CPU throttling needs a debugging connection that this setup does not have), and a hidden tab (headless Chrome never hides its pages). Both need a real browser, Firefox or Safari for the hidden tab.

**Synthesis**

- **Worker:** plausible in our stack but with no verified recipe. Shared memory is realistically out on GitHub Pages (no headers, and the service-worker workaround is unreliable), but Mordie needs only one worker and small messages, so that rules out parallel search, not a single worker.
- **Wasm:** Beta, Safari support disputed between two sources, no speed evidence and no side-by-side build recipe. Not a candidate now.
- **Keep as is:** fine for a visible tab (Measurement 1).
- **Hidden tab:** main-thread timers drop to about one slice a second in Firefox and Chrome, and once a minute after five hidden minutes in Chrome. By arithmetic from those figures that is about 1% and 0.02% of the visible half-time. Whether a worker escapes this is unverified for Chrome and Safari, and Firefox has a pref to throttle workers. Nothing supports Web Locks as a keep-alive.
- **"When":** the browser cannot let Mordie think while the player is away, whatever "where" says, if hidden tabs are throttled. The web side of an "only while away" mode is therefore not feasible without a result for workers; the terminal has no such limit.
- **Away detection:** the Idle Detection API is permission-gated and of limited availability, and `requestIdleCallback` is missing in Safari, so neither is a base for a feature.
- **Precedent:** pondering needs separate cores (a worker, not the page's thread); Lichess picks engine builds by capability, so a fallback exists.

**Measurement 2: the exact search in a Web Worker, in the project's stack (headless Chrome, visible tab)**

A throwaway Kotlin/JS module (`proto`, in a scratch git worktree outside the repo) runs the same `IdaStarSolver` loop as `BackgroundMordieSearch` and counts nodes, either on the page's thread or in a Web Worker, on a fixed 5x5 board (three boards, 12 s each). The page measured its own timer lag and frame intervals meanwhile, as in Measurement 1.

| Configuration | Nodes per second (3 boards) | Page timer lag p95 / max (ms) | Frame interval p95 / max (ms) |
|---|---|---|---|
| Page thread, 10 ms work / 10 ms rest (today) | 5.94 M, 5.95 M, 5.95 M | 8.2 to 8.3 / 8.6 | 16.7 / 16.8 |
| Worker, 10 / 10 (same duty cycle) | 5.4 M, 5.4 M, 5.4 M | 1.2 / 1.6 | 16.7 to 16.8 / 16.8 |
| Worker, continuous (250 ms slices, no rest) | 12.2 M, 12.3 M, 12.2 M | 1.2 to 1.3 / 1.6 | 16.7 / 16.8 |

- A worker at today's duty cycle searches at the same speed (within 10%) and takes the page's 8 ms delay down to about 1 ms.
- A continuous worker searches about 2.05 times as fast, which is the 50% duty cycle given up, and it still leaves the page untouched. It also keeps one core fully busy, which on a phone costs battery and heat (not measured).
- The bound ruled out after 12 s moved by at most one on these boards (11 to 12), so the search itself isn't much further along; the difference is speed, not a different result.
- **Recipe in our stack.** One Kotlin/JS bundle works as both the page script and the worker script: `main()` checks `typeof window === 'undefined'` and sets up either side; the worker is `new Worker("proto.js")`. No second webpack entry was needed (the community chats suggested one). The real game would need the worker as its own small module so `web.js`'s `main()` doesn't start a game in the worker, and a way to put the file into the web distribution; neither was tried.
- Caveats: Chrome only, headless, a fast Mac, a visible tab. No postMessage cost problem showed up for a small progress message every slice. The hidden-tab behaviour, and a slow phone, are not covered.

**Measurement 3: hidden tab in Firefox 159 (macOS), run by the user**

A plain-JS page (throwaway, scratchpad) counts 10 ms work slices per second, once on the page's thread and once in a Web Worker, both with 10 ms of rest after each slice, as the game's Mordie does. Tab in front for 20 s, hidden for about 130 s, in front again for 20 s.

| Tab | Rows | Page slices per second | Worker slices per second |
|---|---|---|---|
| Visible | 41 | 51.2 | 50.1 |
| Hidden | 65 | 1.0 | 51.3 |

- The page's loop drops to one slice a second when the tab is hidden (about 2% of its visible rate), exactly the 1 s minimum MDN documents for Firefox. It recovers at once when the tab is shown again.
- The worker's loop was not throttled at all for the whole 130 s: 51 slices a second hidden, the same as visible. So in Firefox a worker escapes the throttling that the page's thread suffers.
- Not covered: Chrome (intensive throttling after 5 hidden minutes) and a hidden time longer than about 2 minutes.

**Measurement 4: hidden tab in Safari 26.4 (macOS), run by the user**

Same page, tab in front for 24 s, hidden for about 120 s (the page's own timer was so throttled that rows are 2 to 40 s apart, so the page's summary line, which averages rows, is skewed by the first rows; the series below is what counts), in front again for 21 s.

| Tab | Page slices per second | Worker slices per second |
|---|---|---|
| Visible | about 43 | about 45 |
| Hidden, first seconds | 16, then 0.9 to 1.6 | 45, then 26 |
| Hidden, from 28 s on | 0 to 0.5 | 8 to 9, steady for 2 minutes |
| In front again | 43 within a second | 14, then 45 within two seconds |

- Safari throttles both, but the worker keeps about 20% of its visible rate (8 to 9 against 45 slices per second) while the page's thread is down to about 1% or less, and both recover within seconds of showing the tab.
- Unlike Firefox, Safari doesn't leave a hidden worker at full speed. iOS Safari, which reportedly suspends pages outright, was not tested.

**Evaluation against the constraints (RESEARCH.md step 3)**

Constraints that decide it: a static site on GitHub Pages (no response headers, so no cross-origin isolation and no shared memory or Wasm threads), no backend, the project's stack (Kotlin/JS today; Kotlin/Wasm would be a new Beta target), a solo developer and a hobby prototype, and the browser rule for measurements.

| Option | Fit | What could go wrong |
|---|---|---|
| A. Keep the search on the page's thread | Zero cost, and the visible tab is fine (at most 9 ms delay, no dropped frame) | Hidden tabs reduce it to about 2% (Firefox) or 1% or less (Safari) of its rate, so Mordie almost stops while the player is away; the fast solver's steps would also crawl when hidden (one step a second in Firefox, unmeasured for 9x9 in Kotlin) |
| B. Web Worker for the search | Good. Works on plain static hosting, the same Kotlin code and `IdaStarSolver` run unchanged, one bundle can be both page and worker (prototype). Page delay 8 ms to 1 ms; same speed at today's duty cycle, twice as fast continuous; keeps about 100% (Firefox) or about 20% (Safari) of its rate when hidden | A new build piece to package into the web distribution (untried); a continuous worker keeps a core busy (battery on phones, unmeasured); Chrome and iOS Safari hidden behaviour unverified; no unit-test route in CI for the worker itself (browser tests are disabled in CI) |
| C. Kotlin/Wasm | Poor today. Beta, Safari support disputed between two sources, no speed evidence, no known side-by-side build recipe | Adds a build target for an unproven gain |
| D. Shared-memory threads (SharedArrayBuffer, Wasm threads) | Not available. Needs COOP/COEP headers, which GitHub Pages can't set (an open request since 2022, workaround unreliable) | Would need a different host |

**Recommendation (draft, for the user's approval)**

1. **Where: run the browser's search in a Web Worker** (option B). It is the only candidate that fixes both the page delay and, by far the best of the options, hidden-tab speed, with no new constraint on hosting. Start at today's 10 ms / 10 ms duty cycle (the same speed, about 1 ms of page delay) and decide a continuous worker only with a phone battery check. Package the worker as its own small module, so the game's `main()` doesn't start in the worker.
2. **When: no special "away" mode for now.** With a worker, Mordie keeps thinking while the tab is hidden at whatever rate the browser allows (about 100% in Firefox, about 20% in Safari, Chrome and iOS unverified), so the "keeps thinking while you're away" behaviour comes with option B for free. A deliberate mode (think only while hidden or idle) would be a product decision for a later ticket; away detection is not a problem (the tab's visibility state tracked correctly in both runs, and the Idle Detection API isn't needed).
3. **"Where" and "when" call for the same answer:** the worker. The page's thread can't give "when" at all.
4. **Not recommended:** Kotlin/Wasm (revisit when it leaves Beta and Safari support is settled), shared-memory threads (hosting rules them out), and any web-only keep-alive trick (no source supports one).
5. **Standing constraint to add to `docs/CONSTRAINTS.md`:** the web client is hosted on GitHub Pages (static files, no custom response headers), so no cross-origin isolation, hence no shared memory between page and worker and no Wasm threads.
6. **Suggested follow-up tickets:**
   - Run Mordie's search in a Web Worker in the browser client: the worker module, the message protocol (progress and the solution), packaging into the web distribution, and a browser check (hidden tab on Chrome and on a phone) as its manual checklist. It does not depend on GH-213; the fast solver would run in the same worker.
   - Only if wanted: a Mordie "thinks while you're away" mode as a product feature, once the worker is in.
7. **Open points for those tickets:** Chrome's behaviour for hidden workers (intensive throttling after 5 minutes is documented for timers on the page, workers not mentioned); iOS Safari suspension; battery cost of a continuous worker; how the worker file is packaged into the web distribution.

No ADR: the hosting limit goes into `docs/CONSTRAINTS.md`, and the rest is a recommendation for tickets.

## Debrief summary

### 2026-11-01

**What went well**
- The agent ran the experiments end to end: the page-lag measurement in headless Chrome reusing the web harness, a Kotlin/JS worker prototype in the project's own stack (a scratch worktree, nothing in the repo), and a plain-JS page for the hidden-tab check. This is the "measure in the project's own stack" rule from GH-116 in use.
- The user's share was short: two browser runs (Firefox and Safari).
- Measuring settled what the survey left thin: whether a worker is throttled in a hidden tab (Firefox: no; Safari: down to about 20%), and a worker recipe the sources lacked (one Kotlin/JS bundle serves as both page and worker script).

**What was hard or surprising**
- The survey had no verified source on worker throttling, so the recommendation rests on the user's two runs; Chrome and iOS Safari remain unchecked.
- The hidden-tab check needs real browsers (headless Chrome never hides a page), so it was handed to the user; the user found that surprising but expected, as a developer of the game.
- The two-minute wait had no timer, so the user set one on their phone.

**What to change**
- `docs/workflows/RESEARCH.md`: for a check that needs the user's browser and a wait, give a countdown on the page and a spoken cue from the agent, with the page itself silent.
