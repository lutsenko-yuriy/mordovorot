# ADR-0006 — play offline from a cache-first service worker that waits, and let only Update switch versions

## Status
`accepted`

## Context
GH-262 makes the game open and play with no connection, and tells the player when a new version is ready. The site is static files on GitHub Pages with no custom headers (`docs/CONSTRAINTS.md`), and saves live in `localStorage`, which an update must never touch. A service worker is the browser's mechanism for both: it answers the page's requests from a cache it fills, and the browser re-fetches the worker script (skipping the HTTP cache) on every page load and on `registration.update()`, installing a new worker beside the running one when its bytes differ. An installed worker does not take over while a tab of the old version is open; it waits.

## Decision
- **Cache first.** The worker answers the game's own files from its cache and sends everything else (source maps, other origins) to the network. It does not call `clients.claim()`, so a page that loaded from the network keeps its network files.
- **The worker waits, and only Update releases it.** An installed worker sits in `registration.waiting`; that is what "ready" means, since install downloads every file first and fails as a whole if one is missing. The page's `Update` sends it `skip-waiting`, and the page reloads once it is active. Without a click, the new version opens on the first visit after every tab is closed. An open game never changes version under the player.
- **The worker's URL is fixed forever:** `offline-worker.js`, registered by a relative URL (the public site is under a sub-path, GH-111). An installed worker only ever re-checks its own URL, so a renamed file would strand every installed copy on its last version.
- **The cache name is `mordovorot-<version>-<12 hex of a content hash>`**, generated by `generateOfflineManifest` from the files `:web` ships (the distribution's own inputs), and stamped into the worker so its bytes change exactly when a shipped file does. A merge that changes no shipped file (a docs-only one, say) shows no notice. `checkOfflineManifest` fails the distribution when the list and the dist disagree.
- **Install verifies integrity.** Each file is fetched with `cache: "reload"` (GitHub's CDN may serve the old file for about 10 minutes) and its SHA-256 compared with the manifest; a mismatch fails the install, so a half-propagated deploy is never called ready.
- **Two tabs.** After `Update` in tab A, tab B's notice stays and its `Update` just reloads. Until it does, tab B runs the old `web.js` against the new cache, so its next Mordie search loads the new `mordie-worker.js`. This is accepted: it matters only if the worker's message format changed between the two versions, in which case a change to that format must keep both readable for one version.
- **Where it registers:** wherever the page finds `offline-worker.js`, which only the distribution has. The dev server (`:web:serve`) 404s it and nothing registers.

## Alternatives considered
| Option | Why not chosen |
|---|---|
| The page polls a `version.json` and downloads the files itself | Reinvents install and waiting, and needs its own atomic cache swap; the browser's byte-compare of the worker script gives "all files cached, then waiting" for free. |
| Cache name from the version alone | A deploy without a version bump that changes files would never reach players with a cache. |
| Cache name from the commit | Every merge to `master`, docs-only ones included, would show a notice. |
| `skipWaiting()` on install | The new version would take over a game in progress; `controllerchange` then reloads or leaves a page running half old files. |
| Route each tab to its own version's cache | Fixes the two-tab case but keeps the old cache until its tabs close and passes the version on the worker's URL; complex for a rare case. |
| A hand-written worker script | The project's first production JavaScript, with no CI tests and outside `docs/CODE_STYLE.md`. |
